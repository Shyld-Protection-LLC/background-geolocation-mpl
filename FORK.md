# Shyld's fork of Capgo's background-geolocation

Upstream: [Cap-go/capacitor-background-geolocation](https://github.com/Cap-go/capacitor-background-geolocation) at tag `8.6.5` (commit `26dcd51`), MPL-2.0 (`LICENSE`). Forked for the Shyld store app under decision 0139 (owner, 2026-11-19: N2-1 and N2-2).

Every file here is covered by the MPL and carries its notice. They are published unchanged in the public mirror `Shyld-Protection-LLC/background-geolocation-mpl` (the owner's yes, 2026-11-19) at each store build (`pnpm --filter @shyld/plugin-background-geolocation mirror <dir>` gathers them). Nothing outside this folder is covered: Shyld's outbox (`../outbox`) receives the fixes over a process-local hand-off and is not part of this work.

## What Shyld changed

- **The hand-off.** `ShyldHandOff` on Android (`android/.../ShyldHandOff.java`) and iOS (`ios/Sources/.../ShyldHandOff.swift`), called once for each accepted fix, where upstream receives it (`BackgroundGeolocationService.handleLocationChanged`, `locationManager(_:didUpdateLocations:)`). Android finds `com.shyld.plugins.outbox.Outbox.onLocation` by name; iOS posts the `ShyldOutboxLocation` notification. On Android, `onTaskRemoved` also calls `com.shyld.plugins.alerts.Alerts.onAppClosed` by name, so a swipe-away on shift says "Tracking stopped". Without Shyld's plugins in the app, none of it does anything.
- **Keep-alive (decision 0139).** `LocationStore.keepsRunning` replaces upstream's `isEnabled` where the service decides whether to outlive the app (`onUnbind`, `onTaskRemoved`, `onStartCommand`, the plugin's `handleOnDestroy` and orphan stop). It is native delivery, or Shyld's outbox tracking a shift with its `keepTrackingAfterSwipe` switch on (`ShyldHandOff.keepTracking`, by name). `saveSetup` keeps the watcher's title, message, distance filter, interval and fallback without a URL, so a sticky restart can resume; native delivery still needs a URL. "Tracking stopped" is said only when tracking really ends.
- **No Always location (iOS).** Every `requestAlwaysAuthorization` call is gone: `handlePermissions` and the permission request ask When In Use only (no escalation), and geofence setup refuses at once, since geofencing needs Always. Shyld's design never asks for Always or background location, and Apple's scan (ITMS-90683) flags any build that calls it without the Always purpose string. Android declares no `ACCESS_BACKGROUND_LOCATION`, so its `backgroundLocation` alias can't be granted.
- **Re-attach on reload (BL-088).** `start()` while tracking already runs no longer rejects `ALREADY_STARTED` (upstream's behaviour): `reattach` gives the running session's fixes to the new call's callback, lets the earlier one go and sends the last known fix at once (Android: the fused last location when a screen is up; iOS: the manager's last valid fix). The session, its options and the hand-off are untouched, so a page reloaded by a live update gets fixes again without a cold start. Upstream still rejects while a permission request or an orphan stop is in flight, and so does the fork. Tests: `BackgroundGeolocationReattachTest` (Android), `testReattachHandsFixesToTheNewCallback` (iOS).
- **Network fallback on by default (BL-092).** `networkFallback` defaults to on at `start()` and in `LocationStore` (upstream: off), so Android takes a network fix when GPS has been quiet for 20 s (within 300 m). A Pixel indoors on a test shift posted nothing on GPS alone, and with approximate location only GPS_PROVIDER is refused. That refusal, and a network one, are now logged rather than ignored. Tests: `NetworkFallbackDefaultTest`.
- **diagnostics() (BL-092).** A Shyld method on Android, iOS and web: whether the tracker runs (Android: whether its service reached the foreground), the last fix time and the last error. Android keeps the failures upstream only logged or swallowed (a failed `startForeground`, refused GPS or network updates, `start()`'s refusals and start failures) in `ShyldDiagnostics`; iOS keeps location errors. `start()` reports its failures only to its callback, so this is how the app and support see them. Tests: `ShyldDiagnosticsTest`.
- **The service makes its own channel (BL-092).** `ensureChannel` runs before each foreground notification. Upstream made the channel only in the plugin's `load()`, so a service started before that posted to a missing channel. Test Lab's `StartPathTest` (androidTest) starts the service from an activity in front and checks it reaches the foreground with its notification.
- **A fallback notification icon (BL-092).** `smallIcon` uses Android's own location icon when the app has no `mipmap/ic_launcher` (or the configured icon). Without a small icon Android refuses `startForeground` and kills the process; the native gate's start-path case hit it in a test APK.
- **Fused fixes indoors, and a searching GPS left alone (BL-092, the Pixel on build 12).** On API 31+ the service also asks LocationManager's `FUSED_PROVIDER` (Wi-Fi, cell and GPS, no Play services), so a phone indoors gets a fix as iOS does; on a Pixel the network provider is off while Google Location Accuracy is, and GPS gets nothing indoors. Fused and network fixes are taken on the same terms (`ShyldFixFilter.accepts`: GPS first, another only after 20 s of GPS silence and within 300 m). The watchdog no longer removes and re-asks the providers before the first fix of a start, which threw away a cold GPS's search every 70 s. A provider that's off is noted in `diagnostics()`. Still and locked, the providers can stay quiet for minutes (the Pixel, 21:10 to 21:17Z, with no fix at all), so after 50 s without a taken fix the service asks for a current location (fused, else network, else GPS; `getCurrentLocation` on API 30+, a single update before), again each 50 s until fixes return. The filter judges it like any other, and an old fix is never re-sent as new. Tests: `ShyldFixFilterTest`.
- **Locked and still, build 13 (BL-092, the Pixel's T1):** a 7-minute gap right after the lock. The Handler's 50 s timer stops while the phone sleeps in Doze, so the current-location ask is also armed with `AlarmManager.setAndAllowWhileIdle` 60 s ahead. Doze honours that alarm, inexactly and at most about once every 9 minutes while idle. The alarm starts the service with `ACTION_FRESH_FIX`, and each taken fix moves it on (`ShyldFixFilter.freshFixDue`). The fallback's accuracy cap stays at upstream's 300 m (`FALLBACK_MAX_ACCURACY_M`): a ±300 m fix may be all a phone has, and it still goes as the heartbeat. A fallback provider that was off when tracking started (the owner's Pixel: fused off as the one-tap turned Location on) is listened to again at the next fresh-fix ask, and its error clears from `diagnostics()` once it works (`ShyldDiagnostics.resolved`). Tests: `ShyldFixFilterTest`, `ShyldDiagnosticsTest`.
- **No fallback cap with approximate location (BL-092, owner via C 11-24):** with approximate only, Android refuses GPS and every fused or network fix is ±2-3 km, so the 300 m cap dropped them all and the phone read "Location not updating". The cap now applies only while precise is granted (`ShyldFixFilter.fallbackCap`); a coarse fix goes, and the screens show "Approximate position". iOS has no such cap. Tests: `ShyldFixFilterTest`.
- **A still phone computes a new fix (BL-092, VALP-1225; owner via C 11-24 ~03:18Z).** Locked and still indoors, the Pixel's position changed twice in 90 minutes, each estimate handed back for an hour: the platform's current-location ask may answer from a held fix, LocationManager's fused provider ran at the platform's default quality, and its repeats kept putting the ask off. With Play services (`ShyldFusedClient`), the ask is `getCurrentLocation` with a max age of 0, balanced (20 s) each minute and high accuracy (30 s) once the same reading has stood 5 minutes (`ShyldFixFilter.freshFixPriority`). A repeat (`ShyldFixFilter.isRepeat`) no longer reschedules the ask, and the fused stream is Play services' at high accuracy (50 s, no closer than 30 s) in place of LocationManager's (`asksFused` is false with Play services). Without Play services, nothing changes. Tests: `ShyldFixFilterTest`.
- **A tracker no shift wants stops itself (BL-092 backstop; N1's word, 11-24 06:26Z).** The owner's About read "Tracker: running" after the app had stopped the outbox for a missed shift. N1 fixed the cause in the app (`n1-tracker-stops`). As defence in depth, the fork asks the outbox with each fix whether it tracks a shift: on Android `Outbox.tracksAShift` by name (`ShyldHandOff.outboxTracking`), on iOS a `reply` dictionary the outbox fills synchronously. After 10 minutes of "no" (`ShyldFixFilter.stopsUntracked`, `ShyldHandOff.stopsUntracked`) the tracker stops as if `stop()` had been called, and `diagnostics()` says why. With no outbox, or an older one that can't say, nothing changes. Tests: `ShyldFixFilterTest`, the outbox's `HandOffSignatureTest`.
- **On the server's stop, the tracker stops at once (BL-092; C, 11-24).** When ingest answers 409 stop_tracking, the outbox untracks the shift and tells the fork directly: on Android `ShyldTracker.outboxStopped(Context)` by name (the outbox's `TrackerHandOff`), which stops the running service on the main thread; on iOS the `ShyldTrackerStop` notification (`ShyldHandOff.stopName`, `OutboxRules.trackerStopName`) with userInfo `tracking`, observed on the main queue. The tracker stops only when the outbox then tracks no shift (`ShyldFixFilter.stopsNow`, `ShyldHandOff.stopsNow`), and `diagnostics()` says "untracked: stopped, the server ended the shift's tracking". The 10-minute backstop above stays for every other way a tracker runs with nothing tracked. Tests: `ShyldFixFilterTest`, `ShyldTrackerSignatureTest`, `ShyldHandOffTests`, the outbox's `TrackerHandOffTest` and `OutboxRulesTests`.
- **A first fix at once (BL-092, build 18; C, 11-24).** Indoors, the Pixel's first row on VALP-1227 came 3 min 3 s after clock-in: nothing asked for a fix at the start, the fused stream runs every 50 s, the first fresh-fix ask waited 50 s, and fixes before the outbox tracked the shift were dropped. Now, at each start and when the outbox begins tracking a shift (`ShyldTracker.outboxStarted`, by name from the outbox's `TrackerHandOff.started`), Play services is asked for a newly computed fix at high, balanced and low-power accuracy at once (max age 0, 10 s each), and its fused stream runs every 5 s (no closer than 2 s, no wait for an accurate fix) for a minute, then returns to 50 s (`ShyldFixFilter.fastStream`, `FIRST_FIX_PRIORITIES`). Without Play services, LocationManager's current-location ask goes at once. Fork `8.6.5-shyld.7`. Tests: `ShyldFixFilterTest`, `ShyldTrackerSignatureTest`.
- **Providers no oftener than every 5 s, and the diagnostics for the gaps (BL-092, build 18; C, 11-24).** LocationManager's GPS and network providers were asked every second, so the GPS chip searched all shift indoors. Now `ShyldFixFilter.providerIntervalMs` gives at least 5 s. `diagnostics()` on Android adds taken fixes by provider, rejections by reason (`ShyldFixFilter.rejection`: "cap", "grace"), fresh-fix and first-fix asks and answers, the alarm's fires, idle mode (a receiver for `ACTION_DEVICE_IDLE_MODE_CHANGED` and, on API 33+, the light one, from onCreate to onDestroy) and `isIgnoringBatteryOptimizations`. Tests: `ShyldFixFilterTest`, `ShyldDiagnosticsTest`.
- **No GPS grace before a GPS fix (BL-092, build 19's VALP-1231; owner via C, 11-25 ~01:05Z).** Upstream set `lastGpsFixAtMs` to the start time in `start()` and in the sticky restart, so for the first 20 s of every start each network and fused fix was turned away as "grace", the first-fix answers included. The Pixel's About read `rejected: {grace: 9}` with no GPS fix at all, and its first row came at +30 s. It now starts at `ShyldFixFilter.LAST_GPS_FIX_AT_START` (0), so the grace only follows a real GPS fix. Fork `8.6.5-shyld.8`. Test: `ShyldFixFilterTest`.
- **A start after the tracker stopped itself is a fresh start (BL-092, build 19's VALP-1233; 11-25 ~01:40Z).** Since build 19 the Android service can stop itself (a 409 stop_tracking, or 10 minutes with nothing tracked) while the plugin stays bound, so `serviceConnectionFuture` stayed set and every later `start()` only re-attached (BL-088): the last fix was handed back, but there was no notification and no tracking. On the owner's Pixel an On my way right after a clock-out tracked nothing, and no restart mended it. `start()` now re-attaches only while a start is in flight or the service's start is in effect (`BackgroundGeolocation.reattaches`, the service's `active`); otherwise the stale connection is dropped and the start is fresh, and a self-stop marks the tracker not running. iOS already clears its manager on a self-stop. Also on both platforms, within 2 minutes of its own start (`START_SETTLE_MS`, `startSettleSeconds`) a 409 no longer stops the tracker: that 409 is the earlier shift's, arriving while the app still fetches the token before the outbox tracks the new shift. The 10-minute backstop still stops a tracker nothing tracks. Fork `8.6.5-shyld.9`. Tests: `BackgroundGeolocationReattachTest`, `ShyldFixFilterTest`, `ShyldHandOffTests`.
- **The package.** `package.json` is Shyld's (`@shyld/plugin-background-geolocation`, version `8.6.5-shyld.N`, sources not built to `dist/`); `src/definitions.ts` is kept as `src/definitions.d.ts` (types only), and `src/index.ts` re-exports it with `export type *`. `android/settings.gradle` is a standalone build's. In `Package.swift` the package and its product are `ShyldPluginBackgroundGeolocation`, the npm name in PascalCase that Capacitor's sync expects (Shyld Dev's first iOS build stopped on it); the target and Swift module keep upstream's `CapgoBackgroundGeolocationPlugin`. The podspec, example app, docs and build scripts are left out (Swift Package Manager only).
- **Notices and checks.** The MPL notice at the top of every source file, formatting by the repo's formatter and lint fixes, two index checks in `src/web.ts` for strict TypeScript, and the web version's route geometry moved unchanged to `src/route-geometry.ts` (the repo keeps TypeScript files under 400 lines).

Upstream's own native uploader (`backendUrl`) and location log stay in the code, unused: Shyld doesn't configure them.

## Updating from upstream

Copy the new tag's files over these, re-apply the hand-off's two calls, keep the notices, run `pnpm --filter @shyld/plugin-background-geolocation test:android`, and bump the version's `-shyld.N`.
